# trdr v0 사용자 저니 맵 — 최초 설치부터

> 작성 2026-08-06. 근거: docs/PRD.md · docs/USER_STORIES.md · docs/MVP_SCOPE.md,
> 목업 v2 2파일(artifacts/2026-08-06_trdr-cockpit-flow.html ·
> 2026-08-06_trdr-surfaces-flow.html, 프레임 10개).
>
> 유저스토리는 "어느 화면에서 무엇을 한다"를 말한다. 이 문서는 그 사이를
> 잇는다 — **앱을 처음 켠 사람이 첫 결과를 손에 쥐기까지 실제로 지나는
> 순서, 그 사이의 대기·실패·이탈 지점.** 목업 v3의 입력이다.
>
> 표기: 목업 열의 ●는 v2에 프레임이 있음, ◐는 프레임 일부만 다룸,
> ○는 프레임이 없음(=v3 후보 또는 의도적 비대상).

## 0. 범위와 배우

| 항목 | 내용 |
|---|---|
| 대상 사용자 | user zero 1명 (relationship-explorer 연구 워크플로) |
| 잠재 사용자 | 저니의 마찰 지점 식별용으로만 고려 — v0 기능 요구로 승격하지 않는다 |
| 플랫폼 | macOS 전용 |
| 저니의 끝 | 전략 1개가 탐색→사전등록→검증→결과까지 완주 (= v0 인수 기준) |
| 저니 밖 | 주문·실행 (v0에 없음) |

배우 3종: **사용자**(사람) · **에이전트**(BYO, CLI·파일로만 조작) · **앱**(자동 동작).

## 1. 전체 지도

```
[P0 준비]  설치 → 첫 실행 → 키 등록 → 데이터셋 수집
[P1 구성]  빈 콕핏 → 관심종목 등록 → 대시보드 배치 → 에이전트 연결
[P2 탐색]  가설 → 스펙 → 백테스트 → 비교·반복
[P3 검증]  등록 초안 → 사전등록 확정 → ①과거 검증(즉시) / ②실전 관찰(대기)
[P4 결과]  결과 리포트 → 폐기·재등록·유지 → 검증 기록 → 이미지 공유
[P5 반복]  아침 루틴 · 데이터 유지 · 장애 복구
```

시간 감각: P0는 **첫날(반나절~며칠, 키 승인 대기가 지배)**, P1은 **첫 세션
30분~2시간**, P2는 **며칠~몇 주**, P3의 실전 관찰은 **몇 주~몇 달**.
저니는 선형이 아니라 P2↔P3을 도는 순환이고, P1의 구성은 P5에서 계속
손질되며, P5는 그 순환 위에 매일 얹힌다.

# P0 — 준비 (설치 ~ 백테스트 가능 상태)

## S1. 설치

| | |
|---|---|
| 트리거 | 앱을 쓰기로 결정 |
| 행위자 | 사용자 |
| 도착 화면 | 없음 (레포 빌드 또는 .app 실행) |
| 사용자가 하는 일 | 레포를 받아 빌드하거나 배포본을 연다 |
| 앱이 하는 일 | 없음 |
| 완료 신호 | 앱 아이콘이 뜨고 실행된다 |
| 실패 경로 | 서명 없는 앱의 macOS 경고 · 런타임(Node·Python) 부재 · 아키텍처 불일치 |
| 관련 US | 없음 — **유저스토리가 비어 있는 구간** |
| 목업 | ○ |

**열린 항목**: v0는 공개 배포가 목표가 아니지만 완료 정의가 "공개 가능한
수준"이다. 설치 경로(빌드 문서만 / 서명된 .dmg)를 언제 정할지 미결.

## S2. 첫 실행

| | |
|---|---|
| 트리거 | 앱 최초 기동 |
| 행위자 | 앱 → 사용자 |
| 도착 화면 | 온보딩 |
| 사용자가 하는 일 | 이 앱이 무엇을 하는지 확인하고 시작을 누른다 |
| 앱이 하는 일 | 작업 폴더(데이터·스펙·검증 기록의 저장 위치)를 정하고 만든다 |
| 완료 신호 | 키 등록 단계로 넘어간다 |
| 실패 경로 | 폴더 권한 없음 · 디스크 여유 부족 |
| 관련 US | US-01 (앞 구간) |
| 목업 | ◐ — 온보딩 프레임은 키 등록부터 시작한다 |

**갭 1 — 작업 폴더**: 데이터·스펙·검증 기록이 로컬 소유라는 것이 제품 명제인데,
그것들이 **어디에 놓이는지 사용자가 정하거나 확인하는 지점이 저니에 없다.**
검증 기록의 불변성 주장은 "그 파일이 어디 있는가"를 사용자가 알아야 성립한다.

**갭 2 — 첫 고지**: 정직성 규율(사전등록·검증)은 첫 사용 이유가 아니라고
PRD가 못박았다. 그렇다면 첫 화면이 파는 것은 데이터·엔진·콕핏이어야 하는데,
현재 온보딩 프레임에는 그 문장이 없다.

## S3. 키 등록

| | |
|---|---|
| 트리거 | 첫 실행 완료 |
| 행위자 | 사용자 (에이전트 불가 — PRD §6.2) |
| 도착 화면 | 온보딩 · 설정 |
| 사용자가 하는 일 | 소스별 키를 입력한다 |
| 앱이 하는 일 | keychain에만 저장하고, 키가 실제로 통하는지 1회 호출로 확인한다 |
| 완료 신호 | 소스별 "등록됨 / 확인됨" 상태. 값은 어디에도 표시되지 않는다 |
| 실패 경로 | 오타 · 미승인 · DART IP 미승인(status 012) · 승인 대기중 · KRX 로그인 만료 |
| 관련 US | US-01, US-18 |
| 목업 | ● 온보딩(키 등록·실패·재개) · ● 수집·설정(키 상태) |

소스가 4종이고 발급 경로가 제각각이다.

| 소스 | 자격증명 | 발급 마찰 |
|---|---|---|
| 금융위 API | 서비스키 | 활용신청 승인 대기 (즉시 아님) |
| DART | API 키 | 키 발급은 즉시, **IP 승인이 별도** — 이 기기에서 현재 실패 상태 |
| KIS | appkey + appsecret | 계좌 필요 · 실시간 세션 ~41종목 상한 |
| KRX | id + pw | 로그인 세션 만료 반복 · 재배포 금지 |

**갭 3 — 키 없이 시작하기**: 승인 대기가 며칠 걸리는 소스가 있는데,
저니에는 "키가 아직 없는 상태로 앱을 써보는" 경로가 없다. 배포 데이터
베이스(상폐 명부·일봉 씨드)만으로 백테스트까지 가능해야 하는지, 아니면
키가 전부 모이기 전에는 아무것도 못 하는지 — **미결이고, 첫날 이탈을
가르는 지점이다.**

**갭 4 — 부분 등록 상태**: 4종 중 2종만 등록됐을 때 앱이 어떤 상태인지
(무엇이 되고 무엇이 안 되는지)를 보여주는 화면이 없다.

## S4. 데이터셋 확보

| | |
|---|---|
| 트리거 | 키 등록 완료(또는 건너뜀) |
| 행위자 | 사용자가 명령 1개 → 앱이 수행 |
| 도착 화면 | 온보딩 · 수집 상태 pane |
| 사용자가 하는 일 | 명령 1개를 실행하고 기다린다 |
| 앱이 하는 일 | 배포 데이터를 내려받고, 개인 키 소스는 직접 수집한다 |
| 완료 신호 | **"백테스트 가능"** 상태 명시 |
| 실패 경로 | KIS 쿼터 초과 · 네트워크 끊김 · KRX 세션 만료 · 중간 중단 |
| 관련 US | US-01, US-02, US-17 |
| 목업 | ● 온보딩(진행률·실패·재개) · ● 수집 상태 |

수집 대상의 무게가 균일하지 않다.

| 데이터 | 범위 | 성격 |
|---|---|---|
| 상폐 명부 | 4,052행 | 배포 씨드 — 즉시 |
| 일봉 이력 | 상폐 포함 | 배포 베이스 + 개인 보강 |
| 수급 11-way | 1999~ 일별 | **KRX 인증 수집 — 저니에서 가장 긴 대기** |
| 공시 | DART | 개인 키 |

**갭 5 — 기다림의 정직한 표기**: 수급 이력은 1999년부터 일별 11분류다.
첫 수집이 몇 분인지 몇 시간인지가 저니 설계를 바꾼다. "진행률 표시"는
스토리에 있지만 **예상 소요·중단 가능 여부·부분 완료로 먼저 쓰기 시작할 수
있는지**가 없다.

**갭 6 — 부분 데이터로 백테스트**: 수급이 아직 2015년까지만 받아졌을 때
2010년 구간 백테스트를 돌리면 어떻게 되는가. 조용히 빈 값으로 도는 것이
가장 나쁜 결과다. **데이터 커버리지와 백테스트 요청 구간의 대조는 정직성
규율의 일부인데 현재 어느 스토리에도 없다.**

# P1 — 구성 (내 화면 만들기)

이 구간이 저니에서 통째로 빠져 있었다. PRD §4.1은 자유 배치와 pane
카탈로그를 요구사항으로 적어 두었지만, **사용자가 빈 화면을 자기 화면으로
바꾸는 행위 자체**는 유저스토리에도 목업에도 없다. 목업의 관심종목 pane은
이미 종목이 들어 있는 상태로만 그려져 있고, 명령 9개(차트·수급·스펙·
백테스트·등록·관찰·기록·수집·설정) 중 **관심종목을 다루는 명령이 없다.**

## S5. 빈 콕핏

| | |
|---|---|
| 트리거 | 데이터셋 준비 완료 |
| 행위자 | 사용자 |
| 도착 화면 | 앱 셸 (기본 프리셋) |
| 사용자가 하는 일 | 화면을 보고 다음에 뭘 할지 찾는다 |
| 앱이 하는 일 | 관심종목 0·전략 0·등록 0의 빈 상태로 다음 행동을 안내한다 |
| 완료 신호 | 사용자가 첫 행동(종목 넣기 또는 가설 만들기)으로 이동한다 |
| 실패 경로 | 빈 화면 앞에서 멈춤 — **이탈 위험 최대 지점** |
| 관련 US | US-03, US-04 |
| 목업 | ◐ — 오늘 프레임에 "가설 만들기" 빈 상태 문구만 있고, 전부 빈 첫 진입 프레임은 없다 |

**갭 7 — 첫 진입 프리셋**: 등록이 0건이면 "내 가설의 오늘"은 전부 비어 있다.
첫 진입 프리셋이 "리서치"여야 하는지, 아니면 관심종목부터 채우게 하는 별도
첫 화면이 있어야 하는지 미결.

## S6. 관심종목 등록

| | |
|---|---|
| 트리거 | 빈 관심종목 pane, 또는 평소 보던 종목을 넣고 싶을 때 |
| 행위자 | 사용자 (에이전트도 CLI로 가능해야 하는지 미결 — 갭 9) |
| 도착 화면 | 관심종목 pane · 명령줄 |
| 사용자가 하는 일 | 종목을 검색해 추가하고, 순서를 바꾸고, 빼고, 묶는다 |
| 앱이 하는 일 | 목록을 저장하고, 실시간 슬롯을 배분하고, 초과분에 지연 라벨을 단다 |
| 완료 신호 | 내 종목들이 시세·수급·공시와 함께 보인다 |
| 실패 경로 | 검색 결과 없음 · 상폐 종목 · 41 슬롯 초과 · 실시간 세션 끊김 |
| 관련 US | US-04 (부분 — 등록 행위 자체는 스토리에 없음) |
| 목업 | ◐ — 채워진 목록과 슬롯 라벨만 있고, 추가·검색·삭제 경로가 없다 |

**갭 8 — 종목이 목록에 들어오는 경로가 정의돼 있지 않다.** 명령 9개에
관심종목 명령이 없고, GUI에도 추가 버튼이 그려져 있지 않다. 결정할 것:
명령줄에 명령을 하나 더 두는가(예: `005930 관심`), 차트를 띄운 뒤 고정하는
방식인가, GUI 검색창인가. **"티커만 입력 = 차트"라는 기존 문법과 가장 잘
붙는 것은 차트 상태에서 관심종목으로 보내는 동작이다.**

**갭 9 — 관심종목과 전략 유니버스의 관계**: 볼 종목을 정하는 출처가 둘이다.

| 출처 | 성격 | 규모 |
|---|---|---|
| 사람이 고른 관심종목 | 수동, 안정적 | 수~수십 |
| 전략 스펙의 유니버스 | 규칙에서 도출, 매일 바뀔 수 있음 | 수십~수백 |
| 관찰 중 전략이 잡은 종목 | 자동, 검증 무결성과 직결 | 가변 |

셋을 한 목록에 섞을지, pane을 나눌지, 라벨로 구분할지가 미결이다. 이건
화면 문제가 아니라 데이터 모델 문제다 — **목업보다 먼저 정해야 한다.**

**갭 10 — 41 슬롯 배분 규칙**: 실시간 상한이 ~41종목인데 위 세 출처의
합은 쉽게 그것을 넘는다. 누가 실시간을 차지하는가 — 사용자가 고정하는가,
관찰 중 전략이 우선인가, 최근 본 순인가. 지금은 "초과분은 지연 라벨"이라는
**결과만 정해져 있고 배분 규칙이 없다.**

**갭 11 — 상폐 종목 검색**: 상폐 포함 데이터가 제품의 차별 요소다. 그러면
종목 검색에서 상폐 종목이 나오는가, 나온다면 관심종목에 넣을 수 있는가
(실시간은 없고 이력만 있는 종목). 백테스트 관점에선 필요하고 시세 관점에선
무의미하다 — 구분 표기가 필요하다.

## S7. 대시보드 배치

| | |
|---|---|
| 트리거 | 기본 프리셋이 내 작업 방식과 맞지 않을 때 |
| 행위자 | 사용자 |
| 도착 화면 | 앱 셸 (dockview) · 설정(프리셋 관리) |
| 사용자가 하는 일 | pane을 추가·제거하고, 드래그로 배치하고, 프리셋으로 저장한다 |
| 앱이 하는 일 | 배치를 저장하고, 프리셋 전환 시 복원한다 |
| 완료 신호 | 내 배치가 이름을 갖고 저장된다 |
| 실패 경로 | 배치를 망가뜨림 → 기본으로 되돌리는 경로 필요 |
| 관련 US | US-04(배치 저장) · US-18(프리셋 저장·삭제) |
| 목업 | ◐ — 설정에 "레이아웃 프리셋 · 내 배치 1 · 관리" 항목만 있다 |

**갭 12 — pane을 추가하는 경로**: pane 카탈로그 8종(관심종목·차트·수급·
공시·관찰·수집 상태·터미널·스펙)이 요구사항에 있는데, **카탈로그를 여는
방법이 없다.** 메뉴인가, 명령줄인가, 빈 영역 우클릭인가.

**갭 13 — 프리셋 저장 흐름**: 설정 화면의 "관리" 버튼 하나로 요약돼 있다.
실제로는 지금 배치를 이름 붙여 저장하는 동작이 앱 셸에서 일어난다.

**갭 14 — pane 사이의 연동**: 관심종목 행을 누르면 차트 pane이 그 종목으로
바뀌는가, 새 차트가 열리는가. 수급·공시 pane도 같이 따라가는가. **"죽은
클릭 금지" 원칙에 걸리는 지점이고, 대시보드가 하나의 화면으로 작동하는지
여러 창의 모음인지를 가른다.**

**갭 25 — 조용한 실패**: 관찰 중인 전략이 있으면 수집 중단은 검증의

정보**로 두면 안 되고, 관찰 중일 때는 오늘 화면이 그것을 끌어올려야 한다.

**갭 26 — 엔진 버전과 재현성**: 앱이 업데이트되어 엔진이 바뀌면 예전 등록의
재현 검증 해시가 달라진다. **재현 검증이 무엇을 보증하는지가 엔진 버전
고정을 포함하는지 미결이다.** v0에서도 첫 업데이트에 바로 부딪힌다.
