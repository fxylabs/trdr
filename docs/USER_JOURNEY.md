# trdr v0 사용자 저니 맵 — 최초 설치부터

> 작성 2026-08-06. 근거: docs/PRD.md · docs/USER_STORIES.md · docs/MVP_SCOPE.md,
> 목업 v2 2파일(artifacts/2026-08-06_trdr-cockpit-flow.html ·
> 2026-08-06_trdr-surfaces-flow.html, 프레임 10개).
>
> 유저스토리는 "어느 화면에서 무엇을 한다"를 말한다. 이 문서는 그 사이를
> 잇는다 — **앱을 처음 켠 사람이 첫 결과를 손에 쥐기까지 실제로 지나는
> 순서, 그 사이의 대기·실패·이탈 지점.** 목업 v3의 입력이다.
>
> 표기: 목업 열의 ●는 v2에 프레임이 있음, ◐는 프레임 일부만 다룸,
> ○는 프레임이 없음(=v3 후보 또는 의도적 비대상).

## 0. 범위와 배우

| 항목 | 내용 |
|---|---|
| 대상 사용자 | user zero 1명 (relationship-explorer 연구 워크플로) |
| 잠재 사용자 | 저니의 마찰 지점 식별용으로만 고려 — v0 기능 요구로 승격하지 않는다 |
| 플랫폼 | macOS 전용 |
| 저니의 끝 | 전략 1개가 탐색→사전등록→검증→결과까지 완주 (= v0 인수 기준) |
| 저니 밖 | 주문·실행 (v0에 없음) |

배우 3종: **사용자**(사람) · **에이전트**(BYO, CLI·파일로만 조작) · **앱**(자동 동작).

## 1. 전체 지도

```
[P0 준비]  설치 → 첫 실행 → 키 등록 → 데이터셋 수집
[P1 진입]  빈 콕핏 → 에이전트 연결
[P2 탐색]  가설 → 스펙 → 백테스트 → 비교·반복
[P3 검증]  등록 초안 → 사전등록 확정 → ①과거 검증(즉시) / ②실전 관찰(대기)
[P4 결과]  결과 리포트 → 폐기·재등록·유지 → 검증 기록 → 이미지 공유
[P5 반복]  아침 루틴 · 데이터 유지 · 장애 복구
```

시간 감각: P0는 **첫날(반나절~며칠, 키 승인 대기가 지배)**, P2는 **며칠~몇 주**,
P3의 실전 관찰은 **몇 주~몇 달**. 저니는 선형이 아니라 P2↔P3을 도는 순환이고,
P5는 그 순환 위에 매일 얹힌다.

# P0 — 준비 (설치 ~ 백테스트 가능 상태)

## S0. 설치

| | |
|---|---|
| 트리거 | 앱을 쓰기로 결정 |
| 행위자 | 사용자 |
| 도착 화면 | 없음 (레포 빌드 또는 .app 실행) |
| 사용자가 하는 일 | 레포를 받아 빌드하거나 배포본을 연다 |
| 앱이 하는 일 | 없음 |
| 완료 신호 | 앱 아이콘이 뜨고 실행된다 |
| 실패 경로 | 서명 없는 앱의 macOS 경고 · 런타임(Node·Python) 부재 · 아키텍처 불일치 |
| 관련 US | 없음 — **유저스토리가 비어 있는 구간** |
| 목업 | ○ |

**열린 항목**: v0는 공개 배포가 목표가 아니지만 완료 정의가 "공개 가능한
수준"이다. 설치 경로(빌드 문서만 / 서명된 .dmg)를 언제 정할지 미결.

## S1. 첫 실행

| | |
|---|---|
| 트리거 | 앱 최초 기동 |
| 행위자 | 앱 → 사용자 |
| 도착 화면 | 온보딩 |
| 사용자가 하는 일 | 이 앱이 무엇을 하는지 확인하고 시작을 누른다 |
| 앱이 하는 일 | 작업 폴더(데이터·스펙·검증 기록의 저장 위치)를 정하고 만든다 |
| 완료 신호 | 키 등록 단계로 넘어간다 |
| 실패 경로 | 폴더 권한 없음 · 디스크 여유 부족 |
| 관련 US | US-01 (앞 구간) |
| 목업 | ◐ — 온보딩 프레임은 키 등록부터 시작한다 |

**갭 1 — 작업 폴더**: 데이터·스펙·검증 기록이 로컬 소유라는 것이 제품 명제인데,
그것들이 **어디에 놓이는지 사용자가 정하거나 확인하는 지점이 저니에 없다.**
검증 기록의 불변성 주장은 "그 파일이 어디 있는가"를 사용자가 알아야 성립한다.

**갭 2 — 첫 고지**: 정직성 규율(사전등록·검증)은 첫 사용 이유가 아니라고
PRD가 못박았다. 그렇다면 첫 화면이 파는 것은 데이터·엔진·콕핏이어야 하는데,
현재 온보딩 프레임에는 그 문장이 없다.

## S2. 키 등록

| | |
|---|---|
| 트리거 | 첫 실행 완료 |
| 행위자 | 사용자 (에이전트 불가 — PRD §6.2) |
| 도착 화면 | 온보딩 · 설정 |
| 사용자가 하는 일 | 소스별 키를 입력한다 |
| 앱이 하는 일 | keychain에만 저장하고, 키가 실제로 통하는지 1회 호출로 확인한다 |
| 완료 신호 | 소스별 "등록됨 / 확인됨" 상태. 값은 어디에도 표시되지 않는다 |
| 실패 경로 | 오타 · 미승인 · DART IP 미승인(status 012) · 승인 대기중 · KRX 로그인 만료 |
| 관련 US | US-01, US-18 |
| 목업 | ● 온보딩(키 등록·실패·재개) · ● 수집·설정(키 상태) |

소스가 4종이고 발급 경로가 제각각이다.

| 소스 | 자격증명 | 발급 마찰 |
|---|---|---|
| 금융위 API | 서비스키 | 활용신청 승인 대기 (즉시 아님) |
| DART | API 키 | 키 발급은 즉시, **IP 승인이 별도** — 이 기기에서 현재 실패 상태 |
| KIS | appkey + appsecret | 계좌 필요 · 실시간 세션 ~41종목 상한 |
| KRX | id + pw | 로그인 세션 만료 반복 · 재배포 금지 |

**갭 3 — 키 없이 시작하기**: 승인 대기가 며칠 걸리는 소스가 있는데,
저니에는 "키가 아직 없는 상태로 앱을 써보는" 경로가 없다. 배포 데이터
베이스(상폐 명부·일봉 씨드)만으로 백테스트까지 가능해야 하는지, 아니면
키가 전부 모이기 전에는 아무것도 못 하는지 — **미결이고, 첫날 이탈을
가르는 지점이다.**

**갭 4 — 부분 등록 상태**: 4종 중 2종만 등록됐을 때 앱이 어떤 상태인지
(무엇이 되고 무엇이 안 되는지)를 보여주는 화면이 없다.

## S3. 데이터셋 확보

| | |
|---|---|
| 트리거 | 키 등록 완료(또는 건너뜀) |
| 행위자 | 사용자가 명령 1개 → 앱이 수행 |
| 도착 화면 | 온보딩 · 수집 상태 pane |
| 사용자가 하는 일 | 명령 1개를 실행하고 기다린다 |
| 앱이 하는 일 | 배포 데이터를 내려받고, 개인 키 소스는 직접 수집한다 |
| 완료 신호 | **"백테스트 가능"** 상태 명시 |
| 실패 경로 | KIS 쿼터 초과 · 네트워크 끊김 · KRX 세션 만료 · 중간 중단 |
| 관련 US | US-01, US-02, US-17 |
| 목업 | ● 온보딩(진행률·실패·재개) · ● 수집 상태 |

수집 대상의 무게가 균일하지 않다.

| 데이터 | 범위 | 성격 |
|---|---|---|
| 상폐 명부 | 4,052행 | 배포 씨드 — 즉시 |
| 일봉 이력 | 상폐 포함 | 배포 베이스 + 개인 보강 |
| 수급 11-way | 1999~ 일별 | **KRX 인증 수집 — 저니에서 가장 긴 대기** |
| 공시 | DART | 개인 키 |

**갭 5 — 기다림의 정직한 표기**: 수급 이력은 1999년부터 일별 11분류다.
첫 수집이 몇 분인지 몇 시간인지가 저니 설계를 바꾼다. "진행률 표시"는
스토리에 있지만 **예상 소요·중단 가능 여부·부분 완료로 먼저 쓰기 시작할 수
있는지**가 없다.

**갭 6 — 부분 데이터로 백테스트**: 수급이 아직 2015년까지만 받아졌을 때
2010년 구간 백테스트를 돌리면 어떻게 되는가. 조용히 빈 값으로 도는 것이
가장 나쁜 결과다. **데이터 커버리지와 백테스트 요청 구간의 대조는 정직성
규율의 일부인데 현재 어느 스토리에도 없다.**

# P1 — 첫 진입

## S4. 빈 콕핏

| | |
|---|---|
| 트리거 | 데이터셋 준비 완료 |
| 행위자 | 사용자 |
| 도착 화면 | 앱 셸 (프리셋 "내 가설의 오늘") |
| 사용자가 하는 일 | 화면을 보고 다음에 뭘 할지 찾는다 |
| 앱이 하는 일 | 전략 0·등록 0의 빈 상태로 다음 행동을 안내한다 |
| 완료 신호 | 사용자가 첫 행동(가설 만들기)으로 이동한다 |
| 실패 경로 | 빈 화면 앞에서 멈춤 — **이탈 위험 최대 지점** |
| 관련 US | US-03, US-04 |
| 목업 | ◐ — 오늘 프레임은 있으나 등록 0건 빈 상태가 주인공인 프레임은 없다 |

**갭 7 — 첫 진입 프리셋**: 등록이 0건이면 "내 가설의 오늘"은 전부 비어 있다.
첫 진입 프리셋은 "리서치"여야 하는 것 아닌가. 미결.

## S5. 에이전트 연결

| | |
|---|---|
| 트리거 | 첫 가설을 형식화하려는 시점 |
| 행위자 | 사용자 → 에이전트 |
| 도착 화면 | 터미널 pane |
| 사용자가 하는 일 | 터미널 pane에서 자기 에이전트(Claude Code·Codex 등)를 띄운다 |
| 앱이 하는 일 | trdr CLI를 PATH에 노출하고, 작업 폴더를 에이전트 작업 디렉토리로 준다 |
| 완료 신호 | 에이전트가 `trdr` 명령을 실행해 응답을 받는다 |
| 실패 경로 | CLI 미설치 · 에이전트가 trdr 사용법을 모름 · 잘못된 폴더 |
| 관련 US | US-05, US-06, US-12 |
| 목업 | ○ |

**갭 8 — 이 저니에서 가장 큰 빈칸.** 제품 명제가 "에이전트 퀀트 개발의
인프라"인데, **에이전트를 처음 붙이는 순간이 유저스토리에도 목업에도
없다.** PRD §6.2는 에이전트가 무엇을 할 수 있는지만 규정한다. 필요한 것:

- 에이전트가 trdr 사용법을 어디서 읽는가 (앱이 생성하는 지침 파일 / CLI `--help` / 둘 다)
- 앱 실행 중임을 에이전트가 아는 방법 (로컬 소켓 규약)
- 에이전트를 바꿔도 같게 동작한다는 것을 사용자가 확인하는 지점

# P2 — 탐색

## S6. 가설 → 스펙

| | |
|---|---|
| 트리거 | 사용자가 아이디어를 말한다 |
| 행위자 | 사용자 → 에이전트 |
| 도착 화면 | 터미널 pane · 명령줄(Tab 전환) · 스펙 pane |
| 사용자가 하는 일 | 자연어로 가설을 말하고, 형식화된 스펙을 읽고 고친다 |
| 앱·에이전트 | 에이전트가 .trdr.yaml을 쓰고, 앱이 1초 내 핫리로드한다 |
| 완료 신호 | 스펙 pane과 차트 오버레이가 가설을 반영한다 |
| 실패 경로 | 스펙 문법 오류 · **에이전트가 가설을 잘못 해석** |
| 관련 US | US-05, US-06 |
| 목업 | ◐ — 명령줄 프레임은 있으나 스펙 오류 표기 상태가 없다 |

**갭 9 — 오해의 발견**: 문법 오류는 표기 규칙이 있다(US-06). 문법은 맞는데
의도가 다르게 형식화된 경우가 실제로 더 흔하다. 사용자가 스펙을 **읽고
확인하는** 지점이 저니에 명시돼야 한다 — 사전등록 화면에서 처음 알아채면
너무 늦다.

## S7. 탐색 백테스트

| | |
|---|---|
| 트리거 | 스펙 준비됨 |
| 행위자 | 사용자 또는 에이전트 |
| 도착 화면 | 명령줄 · 백테스트 리포트 |
| 사용자가 하는 일 | `005930 백테스트` 를 친다 |
| 앱이 하는 일 | 결정론 백테스트를 돌리고 비용 가정·구간을 리포트에 명시한다 |
| 완료 신호 | 리포트가 뜨고 **"탐색"** 라벨이 붙어 있다 |
| 실패 경로 | 데이터 미커버 구간 · 상폐 종목 처리 · 스펙이 아무 신호도 내지 않음 |
| 관련 US | US-07 |
| 목업 | ◐ |

## S8. 비교·반복

| | |
|---|---|
| 트리거 | 첫 결과가 만족스럽지 않다 |
| 행위자 | 사용자 ↔ 에이전트 (수 회~수십 회) |
| 도착 화면 | 프리셋 "리서치" |
| 사용자가 하는 일 | 파라미터·기간·종목을 바꿔가며 결과를 나란히 본다 |
| 앱이 하는 일 | 비교 축을 고정하고, 전부 탐색 결과임을 라벨로 구분한다 |
| 완료 신호 | 등록할 만한 후보 1개를 고른다 |
| 실패 경로 | **과최적화** — 반복이 곧 자기 기만이 되는 구간 |
| 관련 US | US-08 |
| 목업 | ● 리서치 비교 |

**갭 10 — 반복 횟수**: 사전등록이 막으려는 자기 기만은 **바로 이 구간에서
생긴다.** 같은 데이터로 40번 돌려 제일 좋은 것을 등록하면 사전등록은
형식만 남는다. 앱은 그 40번을 이미 알고 있다(전부 로컬 기록). **탐색
반복 횟수·탐색 구간을 등록 화면에 그대로 얹는 것이 v0에서 가능한 가장
정직한 장치인데 현재 어느 문서에도 없다.** 결정 필요.

# P3 — 등록과 검증

## S9. 등록 초안

| | |
|---|---|
| 트리거 | 후보 확정 |
| 행위자 | 에이전트 (또는 사용자 직접) |

| 관련 US | US-12 |
| 목업 | ● 사전등록 |

## S10. 사전등록 확정

| | |
|---|---|
| 트리거 | 사용자가 등록 화면을 본다 |
| 행위자 | **사용자 전용** (GUI 클릭만) |
| 도착 화면 | 등록 화면 |
| 사용자가 하는 일 | 고정되는 것(해시·시각·구간)을 전부 읽고, 검증 모드를 고르고, 확정한다 |
| 앱이 하는 일 | 검증 기록에 등록을 쓴다. 삭제·편집 경로 없음 |
| 완료 신호 | 등록 도장 + 검증 기록에 행 1개 |
| 실패 경로 | 확정 후 실수 발견 → 되돌릴 수 없다. 재등록만 가능 |
| 관련 US | US-09, US-10, US-13 |
| 목업 | ● 사전등록(2모드) |

**갭 11 — 구간 겹침 경고**: 과거 검증(holdout)을 고르면서 탐색에 이미 쓴
구간을 검증 구간으로 지정할 수 있다. 그러면 검증이 아니다. **앱은 탐색
이력을 알고 있으므로 겹침을 확정 전에 알려줄 수 있다.** 현재 없다.

**갭 12 — 확정의 무게**: 되돌릴 수 없는 유일한 행동인데, 확정 직전의
마지막 확인 방식(2단 확인 / 요약 재표시 / 없음)이 정해지지 않았다.
"강제·봉인 어휘 금지" 원칙과 충돌하지 않는 표현을 찾아야 한다.

**갭 13 — 결손된 관찰의 처리**: 저니에서 가장 긴 구간이고, 그 사이 데이터
수집이 실패할 확률은 낮지 않다(KRX 세션 만료·KIS 쿼터). 관측이 빠진 날이
있는 결과가 유효한가, 무효인가, 라벨을 다는가. **미결이고, 검증 기록의
신뢰가 여기 걸린다.**

**갭 14 — 앱을 켜지 않는 사이**: 관찰이 앱 실행 중에만 도는지, 백그라운드
수집으로 도는지가 정해지지 않았다. 며칠 안 켜면 결손이 생기는 구조라면
그 사실을 등록 시점에 고지해야 한다.

카드가 그 역할인지 명시돼야 한다.

|---|---|

| 도착 화면 | 수집 상태 pane · 설정 |

| 앱이 하는 일 | 소스별 최신 일자·건수·실패를 보여준다. 부분 완료분은 보존 |

**갭 18 — 조용한 실패**: 관찰 중인 전략이 있으면 수집 중단은 검증의
무결성 문제로 번진다(갭 13과 같은 뿌리). 수집 상태를 **보러 가야만 아는
정보**로 두면 안 되고, 관찰 중일 때는 오늘 화면이 그것을 끌어올려야 한다.

**갭 19 — 엔진 버전과 재현성**: 앱이 업데이트되어 엔진이 바뀌면 예전 등록의
재현 검증 해시가 달라진다. **재현 검증이 무엇을 보증하는지가 엔진 버전
고정을 포함하는지 미결이다.** v0에서도 첫 업데이트에 바로 부딪힌다.
